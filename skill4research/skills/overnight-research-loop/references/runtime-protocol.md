# 持续执行、监督和恢复

SKILL.md 规定行为，不能独立维持聊天会话、启动 timer 或让机器不休眠。区分四种状态：文件写好；作业已提交；controller 正在监督并能续接；科学目标取得证据。只有检查到实际运行证据才能说“已设置通宵运行”。

## 启动前的可检查条件

1. 约定时限/结束条件、资源、预算、权限和任务目录；探查现有执行器和可用资源，不干扰其他人的任务。不适用的 GPU/模型字段省略。
2. 确认实验进程可以脱离当前交互窗口，日志和结果写入持久位置。
3. 配置真正的 coordinator 续接机制：宿主支持的持续任务或 wakeup，或用户项目已有允许的 controller。只挂一个 GPU 作业或 cron 检查日志不会自动产生下一轮 idea。
4. 若使用宿主自动化，先发现自动化工具并按其 schema 配置；提示词明确读取 campaign 状态、查活跃作业、结果反思、继续下一合法动作，状态没变化保持安静。需要实时授权的动作不能绕过。
5. 验证一个完整事件周期：controller 被实际触发、读取状态、发现一次作业结束、保存结果、推进下一任务。用已有安全 mock 或低成本试验即可；把验证时间和结果落盘。

若当前环境没有续接能力，可以在当前活跃会话持续推进并运行已授权的 detached 作业，但必须明确无法保证会话结束后仍自动思考与生成实验。不能用虚构运行状态补这个缺口。实际部署时把不足变成具体阻塞与可执行的解决方式；本技能包不预装 scheduler。

## 监督循环

按约定周期检查 scheduler、PID/worker、checkpoint/结果时间戳、日志尾部、指标进度、tracker；tracker 没更新不能单独判作业死掉。记录监督心跳。用户只在完成、失败、显著变化、需要行动时得到通知，后台检查次数与通知次数分开。

长作业期间文献 agent 可研究下一分支、分析已完成观测或复核机制，避免重复启动评估。新证据优先走 [反馈协议](feedback-and-diversity.md)，主动通知相关活跃角色；轮询日志不能替代消息送达和确认。单次交互 wait 不超过约一分钟，继续给有意义进展；后台 timer 可按约定周期工作。

状态例：prepare→propose→gate→challenge/reply→diagnostic/implement→evaluate→reflect→deepen/diversify→propose。同质化进入 mechanism-review；充分反证进入 abandon 并同步相关角色；证据不足可 park；实现失败进入 diagnose。不得仅因一次测试完成转成 campaign complete。

## 并发与恢复

协调者采用单写者/原子锁或项目等价机制防重复 dispatch；锁含 campaign ID、所有者、更新时间，恢复前确认旧 owner 不再活跃。资源份额由协调者分配，agent 并发不自动扩大计算配额。每次派发检查有效版本、未决质询和消息确认；新发现只限制受影响任务。

恢复时先查真实 job 状态，再核对 campaign、artifacts、未决质询及回执；作业仍活跃就接管监督，不重复提交。补送重要未确认反馈，确认活跃 worker 使用最新可执行版本。已完成未归档的结果补登记；未知状态先查询，不能假定失败。没有有效输出才新建 attempt，保留旧错误证据。

截止时间/预算触发后不派新计算；已运行作业按约定完成、checkpoint 或取消。晨报可说明仍有授权作业正在运行；不得宣称从零到早晨不停执行却没有 controller、心跳、状态转移或实验记录。
