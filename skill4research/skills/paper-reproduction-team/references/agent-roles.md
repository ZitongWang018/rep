# 角色、权限与证据争论

协调者维护目标、授权资源、版本、运行状态和交接清单，持续推进未完成项。以下是职责角色，不必同时占用五个进程；领域特定检查项由目标论文决定。训练只是可能的一类执行，统计、仿真、检索、系统评测等使用相应执行证据。

## 权限矩阵

| 角色 | 可负责修改 | 可作出的决定 | 不可作出的决定 |
|---|---|---|---|
| 协调者 | task 状态、队列、资源分配、争议与经验索引 | 授权内调度、暂停受影响分支、安排验证、归档证据判断 | 绕过科学不变量、替独立审计签字、以资源方便静默改目标 |
| 规划者 | plan、配方矩阵、成本和方案修订 | 提议配方与分支、回应审查 | 批准自己的计划、以论文数值指导测试集调参 |
| 独立计划核查者 | plan-review、独立来源笔记、检查策略 | 提出阻断发现、登记偏差、按版本核查计划 | 改计划再自审、凭摘要或已有批准代替原始核查 |
| 执行修改者 | 分配的工作副本、代码/config、run 清单与产物 | 执行已核查版本、故障修复、请求方案变更 | 默改配方、批准自身实现或结果、扩大资源 |
| 独立实现/结果核查者 | implementation/result-review、独立重算产物、检查策略 | 验证实际执行、质疑旧批准、判定证据与结果状态 | 改被审实现后自审、依据执行者成功摘要背书 |

任何角色可提出发现、请求补证据或建议暂停；协调者/实际授权的作业负责人执行资源处置。硬不变量包括证据真实、评估口径透明、配方变更可追溯、资源不越权、作者不自审。协调者无权用投票或截止压力豁免。非关键偏差可以登记后推进，不能把任何疑虑都升级为停工。

## 规划者：从目标展开可执行配方

审视角度：目标实验测什么，哪些变量承载贡献，表格口径与实现路径是否对应；机制、对照、数据、统计是否能真正实现；资源能否完成目标规模。

交接范式：

> 从原论文、附录与作者实现建立目标实验的 recipe-matrix.md 和 plan.md，定位关键证据、冲突和未知项，提出执行、比较、成本与验收口径。区分已证实、推断和用户允许的替代方案，先不启动昂贵运行。

接受批评时逐项回应：认同并修订、证据反驳，或无法确定且限定结论。不能只改措辞隐藏差异。

## 独立计划核查者：从原始来源反向核查

审视角度：原文/附录/代码实际承诺什么；规划者遗漏哪些条件；冲突是否解决；对照与预算是否公平；未知是否被写成事实。先独立提取目标和关键字段，再比对计划，避免以计划作为唯一阅读地图。

交接范式：

> 给你原始论文、代码与目标定位；先独立重建关键配方与验收标准，再核查计划。给证据、影响、支持/反对解释和通过/需修订/证据不足结论。只审查，不代写修复方案。

提供计划是必要审计对象，但不提供期望判定、预设 bug 或要求证明计划正确的措辞。输出 plan-review.md，发现包含 finding_id、来源定位、目标版本、影响和补证据方式。修订核查聚焦变动及关联字段，旧覆盖外的新增项补查。

## 执行修改者：验证计划真的落地

审视角度：配置是否被读取、代码路径是否执行、数据是否一致、恢复是否完整、资源与成本是否符合授权。实现便利不能替代目标证据。

交接范式：

> 按指定已审版本实现、验证与执行，保存源码/config/data 身份和 run 清单。相关烟测后在授权内完成实验。run 绑定 review_id 与版本，配方变更回核查。报告故障、实际执行和原始结果，不自行批准复现成功。

不改变配方的环境/执行故障可授权内修复并登记；改变数值路径、训练量、预处理、评估等目标字段的修复属于配方变更，须重审相应字段。“恢复运行”不自动沿用旧批准。高成本运行前优先独立核查高风险实现。

## 独立实现/结果核查者：从产物重建事实

审视角度：想运行的与实际运行的是否一致，指标是否正确，checkpoint/样本/种子是否选过，结果可否归因于该版本，观察能支持多强结论。直接读原日志、状态、源码、解析配置、数据版本与结果，必要时独立重算。

交接范式：

> 从原始来源与执行产物独立重建实际实验，再比对目标和已审计划。检查指标口径，指出目标/计划可能漏掉的条件、实现问题和证据不足，按 artifact 身份给结论。只审查，不修改被审对象。

输出 implementation-review.md / result-review.md。计划核查者兼此角色时，主动复查曾批准的假设和遗漏，可撤销或缩小旧批准。规划者不作为自己方案的唯一结果核查者。核查者修改过被审对象须另找作者外人员核查；槽位不足顺序更换，不虚构独立性。

## 证据争论与可逆判决

disputes.md 每个争议保存：

1. claim/finding_id、目标和版本、提出者、原证据、影响与可证伪预测。
2. 反驳：反例、相反来源或其他解释，不能只引用地位或旧批准。
3. 回应：证据是否覆盖反驳，哪些已解决、哪些仍未知。
4. 判决：采纳、撤回、限定、补验证或暂不确定；依据、影响、决定者及重开条件。

协调者组织判断与资源取舍，不凭人数/态度裁决事实。证据无法区分时保留分支/未知，在预算内做能改变判断的最小验证。暂用方案须登记偏差和可逆条件。没有证据不等于反对方输了。

## 对活跃 agents 的即时反馈

发现成立或有可信阻断风险时，不等最终报告才通知。通过现有 agent 消息工具发送：`finding_id、target_version、supersedes、证据定位、受影响 run/文件/字段、严重程度、临时决定、允许继续的范围、需要回应的动作`。

通知所有受影响的规划者、核查者、执行者及活跃 worker，收集 ack/当前执行版本。无法触达或未确认时，不派依赖该发现的新工作；先查状态，不能假定消息已改变执行。

- 无关分支继续，不因局部问题全局取消。
- 受影响产物标 pending review，阻断相关后续 dispatch。
- 长作业确实受影响时优先安全 checkpoint/暂停；继续只会浪费或污染结果时按授权终止受影响作业，保留证据和恢复条件。
- 执行者反馈当前 job/版本、完成量和成本；核查者收到漏检/反例后更新检查策略，不能只要求别人修改。

修订后再通知新版本、重审范围、旧结论撤销情况和允许继续的 run。共享文件更新不能代替主动通知。纯运行故障和科学配方问题分别登记、分别处理。

## 状态、版本与经验

建议状态：PLANNING → PLAN_REVIEW → IMPLEMENTING → IMPLEMENTATION_REVIEW → RUNNING → RESULT_REVIEW → COMPLETE。争议/变更进入相关 review，运行故障进入 diagnose。可合并轻量阶段，角色独立性与证据身份保留。

每次 review 记录 review_id、target_manifest/hash、原始证据、发现和状态。dispatch 绑定已审版本，完成后以源码/config/data/evaluator/result 的 manifest/hash 验证。当前产物变化后旧批准标 superseded 或范围受限；重审相应变更和依赖，不机械重审无关部分，不把同一文件名当同一产物。

project-lessons.md 记录规则、适用条件、证据/run/finding、反例、不适用情况、触发检查和撤销条件。反馈给核查者更新策略，并给规划/执行者改变后续行为。一次失败不生成通用禁令，不自动修改个人记忆。按经验增加已证明关键的检查、删去无贡献的重复检查。

无多 agent 工具时按同样产物和版本流程工作，明确独立核查未完成。skill 不提供后台持久在线或额外平台并发。
