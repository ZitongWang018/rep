2026-10-10。这是对已生成 skill 及两个 references 的情境审查；未执行实验、未修改 skill。审查者未参与此 skill 编写。

## 情境与第一步决定

目标是主表 149.5M、TPP200；现有代码运行 74M、TPP20，loss 接近论文。附录 batch 与作者默认配置冲突。资源为 2 GPU、8 小时，用户已授权最终评估。共 4 个 agent 槽位，包括协调者。

**当前核查判定：不能认定主表复现成功，现有产物只能作为缩减实验/基础实现。** 参数量和训练量均不同，loss 相近不补偿协议缺口。若 TPP 按训练 tokens/参数量定义，目标约 29.9B tokens，现有约 1.48B tokens，训练 token 数约相差 20.2 倍；需先核对论文的 TPP 定义，再以实际吞吐估算两卡时限，不能据此直接断言资源必然够或不够。

下一步应按以下顺序行动：

1. 协调者固定主表行、论文版本、代码版本、两卡时限和已授权评估范围。分配三名 agent：规划者、独立计划核查者、执行者；协调者占第四槽。规划者不写实现，后续可承担独立实现/结果核查。
2. 规划者读取主表、对应正文/附录和作者实际 launch/config，重建 architecture、参数量口径、TPP 与 token 总量、global batch、accumulation、学习率/调度及评估。显式标记 74M/TPP20 与目标的偏差。
3. 独立核查者读原始来源。针对 batch 冲突，区分作者默认值和目标表格实际配置，并用 `microbatch × accumulation × world_size` 重建有效 batch；两卡情况下可调整累积以保留 global batch，但保留与调度等相关字段的核查。证据不足时作条件判定，不能默认代码或附录永远优先。
4. 在不启动完整错误配方的前提下，执行者检查模型参数实际计数、数据/token 计数、有效 batch 与解析配置；用目标配置做短烟测测吞吐和显存，给出含训练、checkpoint、评估的总成本估计。8 小时时限不足则报告完整配方缺口，完成授权范围内有价值的缩减验证，不冒称正式复现。
5. 成本可行且关键配方已核查后，冻结版本并正式训练、监测、评估。用户已授权最终评估，按论文协议执行，无需另加一律禁止测试的门槛。若对已有 74M checkpoint 评估，结果仍标明缩减实验；不能根据最终测试差值持续调参后继续称其独立评估。
6. 独立核查者从运行事实、checkpoint、逐样本评估重建结果；分别判协议与数值。无法完成目标训练时给出“不完整/缩减”，不能因计划、烟测、近似 loss 全部正常而升级。

## Skill 行为评价

**通过：** skill 已明确分离协议与数值、处理来源冲突、区分 token/参数/FLOPs、尊重已有最终评估授权、在资源不足时标记缩减实验；四槽位下允许未实现代码的规划者核查结果，能满足作者与审查者分离，没有强制创建五个并发角色。

**轻量改进点：** 当前 references 使用通用“tokens/参数量/训练量”条目，但没有直接列出 TPP→token 总量、global batch→每步 tokens、总 steps 的闭合计算。建议后续加一个可选算术例子，减少把 TPP20 与 TPP200 当成名称差异的风险。这是易用性改进，现有规则足以得出本情境的正确判定。

**剩余执行边界：** 规则要求实际配置、日志、checkpoint 等原始证据，但 skill 本身不会算吞吐、读取论文或提供后台服务。以上是正确的预期行动和决策，未验证真实工具调用、成本或训练结果。没有发现必须增加用户审批或必须阻断已授权评估的过度约束。
